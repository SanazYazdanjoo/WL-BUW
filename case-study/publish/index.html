UX Engineering case study

Welcome Lounge Companion

I work as a tutor in the Welcome Lounge at Bauhaus-Universität Weimar. From that desk, I saw where arrival information and the team's own coordination broke down. I turned what I saw into requirements and built a student journey and a staff workspace around the spreadsheet the team already trusted.

01The situation

Everything a new student needs exists. It is just in too many places.

Every semester, international students arrive in Weimar and work through the same list: health insurance, a room, the semester fee, enrolment, city registration, a bank account, a residence permit. The university publishes all of it, across many pages, PDFs and a WhatsApp group.

The Welcome Lounge tutors fill the gaps in person, while keeping their own work in an Excel file, a shift sheet and chat.

04Designing the workflow

Two front doors to one workbook

For students: a calm path instead of a dashboard

I first explored a home page with recommendations and event promotions, then cut it back to the journey alone. Every extra panel competed with the next step.

  • Official sources stay canonical. Pages are fetched server-side and cached. If a page changes unexpectedly, the last good version is kept.
  • Private by default. No student accounts, no analytics, no server-side profile.

For staff: screens that answer daily questions

“Who's on duty, who needs attention, what's coming up?”
Today. Tutors don't see the summary cards; they only answered questions tutors never ask.
“What do we know about this student?”
Students. One row per student, edited in place.
“When am I working, and am I doing my share?”
Shifts. Your total and the fair share sit above the grid.
“Is the work spread evenly?”
Statistics, for coordinators and above.
fair share =open days × (S1 hours + S2 hours) × tutors per shift÷ tutors

Open days are weekdays in the semester period, plus any weekend day with someone scheduled. Closed days don't count.

Four roles, one ladder, and nobody climbs it alone

There is no IT department to manage accounts, so every permission follows from someone's place on one ladder.

RoleCan do
TutorStudents, own shifts, events, handover
Coordinator+ tutor list, semester setup, statistics, change log, content, backup
Admin+ tutor and coordinator logins
Super AdminEverything, including Admin logins. Exactly one.

No quiet promotions. Nobody can give anyone, including themselves, a role above their own. I found this gap while designing the ladder: a coordinator could have raised their own role and then set a personal login.

05Building with constraints

Keep the spreadsheet. Give it a better front door.

The easy story would be “the old tools are bad, replace them.” The evidence said the team trusted its Excel file. So I kept it and built the interaction layer around it.

What was already there

  • An Excel file the team trusted and knew how to use
  • A handover to the next semester's team, and one developer: me

What I decided

  • One workbook in the university's Nextcloud stays the source of truth
  • Excel and the web workspace read and write the same file
  • The workbook doubles as backup and semester handover document

What it cost

  • Two ways to edit means conflicts: every write is version-checked, and on autosaved fields the second editor chooses “Use mine” or “Use latest”
  • Hand-edited rows can be invalid, which caused the first failure below
  • The online editor needs a save-then-close habit, which I documented
  • The workbook lives on a server I don't run. When it can't be reached, the tab keeps its last data until sign-out or closing and queues everyday edits for the same conflict checks later; admin changes still need a connection

Under the interface

I built both front doors in one codebase. The browser never talks to Nextcloud directly: a small Node API reads and writes the workbook and checks every staff request against the signed-in role.

Interface
React and Vite, in plain JavaScript. Everyday staff edits save field by field.
Data
The team's workbook in Nextcloud, read and written over WebDAV, parsed with ExcelJS and validated on every read.
Access
Four roles checked on the server, a signed session cookie with CSRF protection. Passwords salted and hashed with scrypt, never stored in the workbook.
Runtime & recovery
Node on Vercel. Daily and before-major-change backups in Nextcloud.

06Iteration

Shipping in small loops with the people who run the lounge

Requests from the team during the pilot. I decided how to respond and shipped each change, usually within hours. Most changes removed things.

  • “We don't need check-in.”→Removed it everywhere, and kept old records readable.
  • “Each student should be one row, edited right there.”→Inline editing with autosave and short headers.
  • “I don't want horizontal scroll anywhere.”→Tables fit their container and become cards on narrow screens.
  • “This looks like an error.”→The red fair-share box became an informational blue note.
  • “Who added this student?”→A read-only “Added by” column, back-filled from the activity history.
  • “People should be able to report problems.”→A Feedback button on every workspace page. Messages land in the change log with name and page.

07When things broke

Designing for the failure I actually saw

During the pilot, edits to the workbook stopped showing up on the site. I traced it layer by layer:

  1. One invalid row (a step name typed into the Section column) made the whole workbook fail validation.
  2. The site then quietly fell back to built-in sample steps. They looked real, so the problem was invisible.
  3. Meanwhile the university's document editor had lost its connection, so later edits never reached the file.

What I changed: the server now keeps serving the last valid workbook it has loaded instead of dropping to sample steps (a freshly started server with nothing loaded still falls back to them), and admins see the exact validation message, such as “Content row 4: choose First Step, Useful Info, …”. The fix was mostly about making the system's state readable to the person responsible for it.

A sign-in that crashed for one role only. After I added the Super Admin login, a correct password returned a server error. I reproduced it live, traced it to a helper used before it was defined, and fixed the order. Then I added the missing test and confirmed it fails on the old code and passes on the new.

The lesson: the tutor path had a test and the new role didn't. Every role's sign-in is now tested; tutor and Super Admin through the full API.

09Reflection

What I would keep, and what I would change

Keep: the most useful decision was not a screen. It was keeping Excel as the source of truth. It lowered the risk for the team, gave them a way out, and turned each new feature into a question of presentation instead of migration.

Keep: letting real use drive removals. “We don't need this” was worth more than any feature request.

Change: I would run the tutor survey before building the staff workspace, not after. Being on the team gave me a head start, but some early decisions rested on my own view of the work.

The main lesson

The hardest calls were about what not to build: no new database, no student accounts, no replacement for the Excel file the team already trusted. The engineering went into making that one file safe to share, and the design into making its state readable to the people who rely on it.
